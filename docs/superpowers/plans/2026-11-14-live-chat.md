# Live Chat + AI Assistant Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Visitors on the public site can open a chat bubble. An AI assistant answers first, using only the site's own content. It never invents prices or availability, and it hands quotes, bookings and requests for a person to the Cleaning Partners team, pointing to the quote form. Staff see every chat under a new **Live chat** sidebar item, can take over, hand back, assign, close and delete. Everything is off until the owner turns it on.

**Architecture:** This is a port of James Whitfield's ("JW") final chat, `/Users/nazmulhasansourab/ireland/james-whitfield` (HEAD of `main`). The widget, motion and admin behaviour match JW. The infrastructure is CP's:
- **Server:** a new `server/modules/chat` module (repo, visitor, staff, bot, knowledge, prompt, notify, sweep). Public routes live at `/api/v1/public/chat`, and admin routes are chained into `adminRoutes` at `/api/v1/admin/chat`. Three tables come from one migration.
- **Realtime:** plain polling against a message-id cursor. Every lock, budget, presence record and alert lives in Postgres.
- **Bot:** it replies after the response through `after()`. A Postgres lease serialises generation.
- **Recurring work:** a CP recurring job (`chat-sweep`, every minute) handles auto-close, no-reply alerts and recovery of a stalled bot. A daily job (`purge-chats`) handles retention.
- **Settings:** one operator-only settings key, `chat`, holds the on/off switches and every visitor-facing string.

**Tech Stack:** Next.js 16.4 App Router with Cache Components (rules: `docs/superpowers/notes/nextjs-16-api.md` §0, §2 `after`/`connection`, §7). Also React 19.3 (the `inert` prop), Hono 4 + `zv`, Drizzle + Postgres, AI SDK `ai@7.0.127` (`generateText`, `tool`, `isStepCount`) through `createLanguageModel`, GSAP 3.15 (already a dependency), lucide-react, TanStack Query (admin), React Email + `mailer`, Vitest (`unit` / `dom` / `integration`) and Playwright.

## Global Constraints

- **Off by default.** The seed and the migration store `chat.enabled = false` and `chat.bot.enabled = false`. While the chat is off, no widget markup or JavaScript reaches the page, the public routes return 404, and every public visual baseline (desktop + mobile, `maxDiffPixels: 0`) stays byte-identical. A chat setting that is unpublished, or whose published value no longer validates (`readPublishedSettings` → null), counts as off.
- **No new npm dependency and no new env var.** Use `gsap` 3.15.0 (plain `gsap` with `useLayoutEffect`/`gsap.context`, as JW does; `@gsap/react` is not needed), lucide-react, TanStack Query, and `Intl.DateTimeFormat`.
  - There is no `nuqs`: admin URL state uses `useSearchParams` + `replaceListSearch` from `components/admin/data-table/list-url.ts`.
  - There is no `@date-fns/tz` or `date-fns`: dates use `Intl.DateTimeFormat` with `settings.site.timezone`.
  - There is no `AI_PROVIDER_MOCK`.
- **No therapy features.** There is no crisis detector, crisis notice or crisis email, no health or medical rules, and no health wording. The bot rules are the cleaning rules in Task 4.
- **Public copy comes from settings.** Every visitor-visible string, including aria-labels, placeholders and stored system notices, comes from `settings.chat` and is passed in as props. `components/chat` joins `PUBLIC_DIRS` in `tests/unit/public-literals.test.ts`. The only literals allowed are the ones that guard already allows: class lists, `data-*` values and `TECHNICAL_CONSTS`.
- **Team name (call):** the default `chat.teamName` is **"the Cleaning Partners team"**. It is filled into copy through the `{team}` placeholder. The default bot name is "Assistant". *If wrong:* an admin edits one setting.

### Decisions (call)

| # | Decision | Cost if wrong |
|---|---|---|
| C1 | **Polling, not SSE**, as JW does. The widget polls every 3 s while open and every 20 s while closed (only once a chat exists). It pauses while hidden, wakes on `visibilitychange`/`online`/`focus`, and backs off 3→6→12→24→30 s. The admin list and thread poll every 4 s while visible and 30 s while hidden; the unread count polls every 30 s. CP runs as one standalone Node server behind Dokploy with no sticky sessions, and polling needs neither in-memory fan-out nor reconnect code. | About 20 requests per minute per open panel. If load ever matters, SSE can replace `GET /conversation` behind the same cursor contract without schema changes. |
| C2 | **Linkify** = JW's rules (JW §5) for staff/AI bubbles only. Emails become `mailto:`; phones (9–15 digits) become `tel:` through CP's existing `telHref()` (`lib/interpolate.ts:78`, which also maps a leading `0` to `+353`). The "WhatsApp" rule is kept (`wa.me/<international>`), harmless when unused. **Plus one CP rule:** an exact occurrence of the configured `contact.quoteHref` (e.g. `/contact#quote`) becomes a same-tab link to that href, so the bot's "use our quote form" line is tappable. Arbitrary URLs are never linked. | A missed number stays plain text; a wrong one is a visible `tel:` link to a wrong number. Both are low-risk and confined to one pure function with tests. |
| C3 | **Turnstile** comes from CP's `integrations.turnstile` DB setting, not env. A chat-local `readTurnstile`/`assertHuman` mirrors `server/modules/leads/service.ts:62-99`: unreadable or disabled → no check; a failed token → 422 `VALIDATION_FAILED` with `fieldErrors.turnstileToken`. The site key is exposed by `GET /status`. The check runs only on `POST /start` for a new chat. | If unreadable settings should fail closed, the chat stays open to bots while the integration is broken. That matches leads (no real enquiry lost) and is a one-line change. |
| C4 | **DSAR:** CP has no cross-entity subject-access module, only the lead CSV export by email and per-lead delete. So chat gets its own `GET /admin/chat/export?email=` (JSON download) and `POST /admin/chat/erase {email}` (`chat:manage`, audited), surfaced as a "Privacy request" dialog in the inbox header. Per-chat Delete stays. A shared DSAR module is not built. | Staff run two tools for one request (Enquiries CSV + chat export). A later DSAR module can call `exportChatsForEmail`/`eraseChatsForEmail` unchanged. |
| C5 | **Deferred work:** `server/lib/defer.ts` wraps `after()` from `next/server` (JW verbatim). It is used only on request paths (visitor start/send, staff handback). That is visible in e2e. The fallback is to await `maybeReply` inline with a short timeout. |
| C6 | **Sweep** is a CP `JobDefinition` (`server/lib/jobs/chat-sweep.ts`, `everyMs: 60_000`) in `RECURRING_JOBS`, with JW's three steps (24 h auto-close, 5 min no-reply alert, 90 s resume) using the DB clock. Retention is a separate daily `purge-chats` job. | The tick is 60 s, so alerts and resumes can be up to about 1 min late. Acceptable for a small team. |
| C7 | **Retention default 12 months** (`chat.retentionMonths`, 1–60), counted from `coalesce(closed_at, last_message_at)`. | Too short loses context; too long holds personal data longer than the privacy policy says. The owner edits one setting. |

## Review Focus

1. **A visitor asks "How much for a 3-bed end of tenancy clean on Friday?" and the content gives no price.** Expected: no invented price or date, a one or two sentence reply naming the quote form (`contact.quoteHref`, tappable), `handoffToHuman` called, the handoff notice stored once, and the team emailed once. Pinned in Task 4 (prompt contains the no-invention and quote rules with the real `quoteHref`) and Task 5 (a tool call → exactly one `handoff` notice + one alert).
2. **On a 390 px phone with the sticky CTA bar showing (and with the consent bar showing).** Expected: the launcher sits above the CTA bar, never covering its buttons, and the full-screen sheet covers both when open. Pinned in Task 10 (the launcher `bottom` style uses `--sticky-cta-h`; the site header writes the var from the bar's height, `0px` when hidden) and the e2e mobile step in Task 12.
3. **The owner sets `enabled: true` but does not publish, or a published value stops validating after a schema change, or an admin previews a draft.** Expected: no widget, `/status` 404, no errors in the page. Pinned in Task 3 (`/status` 404 with an unpublished row) and Task 10 (the slot renders nothing for null settings or draft mode).
4. **The owner edits copy:** empties the presets list, removes `{team}` from a template, or writes a 60-character preset label. Expected: no tray toggle when there are no presets (the main row still opens the panel); unknown or missing placeholders leave the text as typed; the label wraps inside the 272 px pill. Pinned in Task 8 (`fillChatText`) and Task 10 (the hint with `presets: []`).
5. **Staff reply while the bot is generating, or two staff reply at the same moment.** Expected: the bot's reply is dropped (`requireBotOwns`), "{name} joined the chat." appears exactly once, and the chat is assigned to the first replier. Pinned in Task 5 (`requireBotOwns` drop) and Task 6 (two concurrent replies → one joined notice).
